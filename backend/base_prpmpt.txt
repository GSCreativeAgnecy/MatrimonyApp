# Build a Production-Ready Matrimony / Matchmaking Backend with FastAPI

You are a senior backend engineer and software architect.

Build a **production-ready matrimonial/matchmaking backend API** using:

* Python 3.12+
* FastAPI
* SQLAlchemy 2.0 (async)
* PostgreSQL
* Alembic
* Pydantic v2
* Redis
* JWT authentication
* pytest
* Docker / Docker Compose
* Ruff
* mypy where practical

The backend will be consumed primarily by a **React Native mobile application**.

Do NOT build everything into one `User` table/model. Use a normalized relational architecture with clear domain boundaries.

---

# 2. Database

Use PostgreSQL.

Use SQLAlchemy 2.0's modern typed declarative syntax:

```python
class User(Base):
    __tablename__ = "users"

    id: Mapped[UUID] = mapped_column(...)
```

Use:

* UUID primary keys
* timezone-aware timestamps
* proper foreign keys
* indexes
* unique constraints
* check constraints where appropriate
* cascading behavior explicitly defined
* PostgreSQL-specific features where beneficial

All schema changes must go through Alembic migrations.

Never modify the database schema manually.

# 42. Important Business Rules

Implement these rules:

### Rule 1

A user cannot swipe on:

* themselves
* blocked users
* deleted users
* banned users

### Rule 2

A blocked user should not appear in:

* recommendations
* search
* likes
* matches
* messaging

### Rule 3

A deleted/banned user should not appear in discovery.

### Rule 4

A private profile must not expose restricted fields.

### Rule 5

A match is created only when two users mutually like each other.

### Rule 6

A user cannot create duplicate active matches.

### Rule 7

Payment status is determined by verified provider webhooks.

### Rule 8

Verification status can only be changed by authorized verification/admin users or trusted backend processes.

### Rule 9

Premium access is determined from subscription state.

### Rule 10

Users cannot modify server-controlled fields such as:

```text
is_verified
verification_status
subscription_status
premium status
payment status
admin role
```

# 46. Critical Requirement

Before writing code, first produce:

```text
1. Final architecture
2. Database ERD / relationship description
3. Complete table list
4. Important enums
5. Foreign-key relationships
6. Index strategy
7. API endpoint list
8. Authentication/authorization design
9. Recommendation architecture
10. Payment/verification architecture
```

Then implement the project phase by phase.

Do not start coding until the architecture has been reviewed for:

* normalization
* security
* scalability
* privacy
* query performance
* extensibility

The final system should be capable of supporting **hundreds of thousands to millions of users** without requiring a complete architectural rewrite.
